# TCP 三次握手与四次挥手
- **Session ID:** net-03-01
- **Course:** NET
- **Tags:** TCP, 握手
- **Started:** 2026-04-06 19:22
- **Ended:** 2026-04-06 19:48

### User
为什么建立连接要三次握手，关闭却要四次挥手？

### Assistant
三次握手让双方确认收发能力并同步序号；关闭时一方 FIN 只表示自己不再发送，另一方可能还有数据，因此 ACK 与 FIN 通常分开发送。

### User
能结合一个具体场景解释吗？

### Assistant
可以。围绕「TCP 三次握手与四次挥手」，一个直观的场景是：客户端 FIN → 服务端 ACK → 服务端处理完数据发 FIN → 客户端 ACK，进入 TIME_WAIT。

### User
这里最容易出错的地方是什么？

### Assistant
最常见的坑是：把 TIME_WAIT 当成异常状态强行清理。它保证最后的 ACK 能重传，并让旧报文失效。

### User
考试里如果换一种问法，我该怎么判断？

### Assistant
先定位协议层次：链路层看帧与 MAC，网络层看地址与路由，传输层看端口、序号和窗口，再按时间线作答。 当题干关键词落在「TCP 三次握手与四次挥手」上时，先写出对象、约束和目标，再套方法。

### User
用一句话帮我记住它。

### Assistant
一句话：握手确认双向可达，挥手等待双向结束。

### User
它和哪个知识点最容易混淆？

### Assistant
最容易混淆的是「SYN Flood 与半连接队列」。区分时先问：讨论的是存储结构、执行过程还是评价指标？

### User
如果放到真实项目里，这个知识点的价值在哪？

### Assistant
长连接复用可以显著减少握手开销。

# TCP 拥塞控制

### User
慢启动、拥塞避免、快重传和快恢复怎么配合？

### Assistant
慢启动指数增大拥塞窗口，到达阈值后线性增长；收到三个重复 ACK 触发快重传与快恢复，避免直接回到慢启动。

### User
能结合一个具体场景解释吗？

### Assistant
可以。围绕「TCP 拥塞控制」，一个直观的场景是：cwnd 从 1 个 MSS 开始翻倍到 ssthresh，之后每个 RTT 增加一个 MSS。

### User
这里最容易出错的地方是什么？

### Assistant
最常见的坑是：把接收窗口和拥塞窗口混为一谈。发送窗口取两者的较小值。

### User
考试里如果换一种问法，我该怎么判断？

### Assistant
先定位协议层次：链路层看帧与 MAC，网络层看地址与路由，传输层看端口、序号和窗口，再按时间线作答。 当题干关键词落在「TCP 拥塞控制」上时，先写出对象、约束和目标，再套方法。

### User
用一句话帮我记住它。

### Assistant
一句话：发送窗口取接收窗口与拥塞窗口的较小值。

它和哪个知识点最容易混淆？

### Assistant
